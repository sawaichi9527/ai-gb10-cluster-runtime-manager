# 27B TP2 on 2026-09-18 image — resolved: cold-start exceeded hardcoded health timeout

> 記錄日期：2026-09-19。狀態：**RESOLVED（2026-09-19 實測確認）**。先前「BROKEN」診斷為誤判；根因是 **`cluster-up` 硬編碼的 2400s health timeout 短於 27b 首次冷啟動（~40 min）**，與 image 本身無關。

## 最終判決（2026-09-19 驗證）

- **H2（fatal import / image 損壞）證偽。** `error_response` ModuleNotFoundError 是 09-11 與 09-18 兩 image 都有的**非致命 plugin-load 雜訊**——健康 35b container 現行 log 也印出同一行 `[__init__.py:72] Failed to load plugin vllm_omni_register_models ... No module named ...error_response`，但 35b 正常 boot → READY。
- **H1（冷啟動超過硬編 2400s）證實。** 09-19 01:39 那次 27b TP2 boot 是 09-18 image 的**首次冷啟動**（無 warm compile / FlashInfer autotune cache），引擎全程無 fatal：
  - weight 載入 29s + drafter 12s、compile/AOT 快取重建、FlashInfer fp4_gemm autotune 22 profiles × 2 rank、PIECEWISE+FULL+dflash2 CUDA graph capture。
  - rank0 於 boot+2405s 完成 init（`Supported tasks: ['generate']` / chat template detected），**`ERROR: health timeout (2400s)` 恰在 rank0 差不多 Ready 的當刻觸發**。
- **修復後重跑（09-19 12:27）**：`HEALTH_TIMEOUT=3600` 生效，本次 warm cache 下 12:32:16 `/health` 200（~4.6 min），`gb10 status` → `ready`（node0+node1 up），`/v1/models` 正常，實作 completion 回 `READY27B`。image 維持 09-18，不需回退。

## 為什麼 01:39 那次「看似 fatal」

ISSUE 最初引用的 `(EngineCore pid=283) ERROR ...` 是**更早另一次 attempt** 的 log（該次容器已移除）；01:39 的 `boot-cluster.27b.log`（EngineCore pid=151/Worker pid=237）本身**沒有 engine 崩潰**，只有 health timeout。先前把 plugin 雜訊跟 timeout 錯併成「image broken」。

## 根因

- `scripts/cluster-up:129-130` 硬編 `2400`（比較與 echo）。H1 情境（無 warm cache 的首次冷啟動）超過它。
- node1 首 boot 的 compile / FlashInfer autotune cache 與 node0 同步重建；autotune 期間 node0 log 有 `shm_broadcast: No available shared memory broadcast block found in 60 seconds` —— 是 rank1 同步等待的正常噪音，非 hang 訊號。

## 修復（commit `4c6b1a2`）

- `scripts/cluster-up:129-130`：`2400` → `${HEALTH_TIMEOUT:-2400}`（profile 可覆寫，預設不變 2400）。
- `cluster-profiles.d/27b.conf`：新增 `HEALTH_TIMEOUT="3600"`（27b 冷啟動較重）。
- 35b 沿用預設 2400（其冷啟動週期遠短，不需覆寫）。
