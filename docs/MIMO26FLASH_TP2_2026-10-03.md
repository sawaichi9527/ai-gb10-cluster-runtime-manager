# MiMo V2.6 Flash MOPD on TP2 — deployment + benchmark (2026-10-03)

New cluster lane **`mimo26flash`**: Xiaomi MiMo-V2.6-Flash-**MOPD** served on the
2-node DGX Spark (GB10, sm_121) TP2 cluster with vLLM + the checkpoint's bundled
DFlash drafter. Cluster-only and exclusive (like `deepseek`); serves the unified
`:1234` OpenAI API as model id **`aeon`**, 256K context, 8-way concurrency.

## 1. Lineage and artifacts

- Recipe: `tonyd2wild/MiMo-V2.6-Flash-DGX-Spark-Recipe` (MIT, commit `13621bb3`).
  vLLM TP2 + DFlash on 2x GB10.
- Image: `ghcr.io/tonyd2wild/vllm-glm53-flash:sm121-v11-dflash2`
  (community image; vLLM `0.1.dev20051+g487ecf187`, torch 2.13, CUDA 13, sm_120).
  Manifest digest `sha256:4def0ef644cb2e9814136dcffd5e385e21bc594f48f3b292234051904abe85a6`.
- Weights: `XiaomiMiMo/MiMo-V2.6-Flash-MOPD` (official MXFP4 QAT), revision
  `2479e2d0029eca9a34cc7e7f55a121925f81908e`, ~166G (154 files, `SHA256SUMS`).
  On both nodes at `$HOME/docker-stacks/models/mimo-v2.6-flash-mopd`.
- Runtime support vendored at `patches/mimo26flash/` (3 patched vLLM sources +
  repaired dflash config; see its `NOTICE.md`), bind-mounted read-only.

### Ship notes

- **Model download** (node0, then rsync to node1 over CX7 at ~350 MB/s): the HF
  download ran 5h34m at ~8-9 MB/s and completed cleanly. `SHA256SUMS` (154 lines)
  was generated locally; 4 files cross-checked against HF LFS sha256 — all match.
- **Image pull**: GHCR/CDN became unusable from this site mid-transfer (~0.1-0.5
  MB/s, repeated `unexpected EOF` on the two largest layers; docker does not
  resume a partial layer, so it looped). Resolved by pulling the *same* image via
  the anonymous mirror **`ghcr.nju.edu.cn`** (~2-5 MB/s, range-capable), verified
  byte-identical by manifest digest, then `docker tag` to the ghcr.io name on both
  nodes. `IMG_SHA256` pins the digest; the image gate passes (it matches the
  digest value in `RepoDigests`).

## 5. Tool-call repetition probe (MOPD)

The reason MOPD exists: on long agent trajectories the RL/base model would answer
one step with dozens–hundreds of tool calls, often identical, instead of waiting
for results (the recipe documents **148 / 446 identical `grep` calls** in single
responses and **659 / 709 calls** replayed from a captured 32K body).

Harness: `scripts/bench-toolcalls.py` — reconstructs the trigger from the recipe's
published description (aggressive agent system prompt, a large file just written,
~32K context, an explicit "continue without stopping" turn), then counts the tool
calls in one non-streaming response and the number of **duplicate** calls
(identical name+arguments). It does **not** use the recipe's captured body (not
shipped), so it is a proxy — read it as "does MOPD still storm?", not a
like-for-like replay.

Live `mimo26flash`, 2026-10-03:

| config | runs | tool calls per response | duplicate calls |
|---|---|---|---|
| normal trigger, temp 1.0, thinking off | 4 | 2, 1, 2, 2 | none (max_dup 1) |
| normal trigger, temp 0.6, thinking off | 4 | 2, 2, 2, 2 | none |
| normal trigger, temp 1.0, thinking on | 2 | 2, 2 | none |
| strong (OMP-style), temp 1.0, thinking off | 3 + 6 | 1, 9, 2 · 2, 1, 5, 2, 1, 1 | none |
| strong (OMP-style), temp 0.6, thinking off | 3 | 1, 2, 2 | none |

Findings:

- **No duplicate tool calls in any run** (`max_dup = 1` throughout) — the
  repetition pathology MOPD targets did not appear.
- Tool calls per response stay small (median 2; worst single run 9 **unique**
  calls / 7,803 tokens). `finish_reason` is always `tool_calls` (normal stop).
- Consistent with Xiaomi's claim that MOPD mitigates tool-call repetition, and
  with the recipe's note that the RL base needed an external `toolcap` guard.
- **Caveat**: without the recipe's captured request body, this is a reconstructed
  trigger. It shows MOPD does not storm here; it is not a controlled MOPD-vs-RL
  A/B (RL was not downloaded). If the pathology ever reappears in a real harness,
  the recipe's `tools/toolcap-proxy.cjs` (`toolCap`, default 6) remains the
  external backstop.

## 6. Multimodal (image / audio / video)

Enabled 2026-10-03 by mounting the prebuilt `soundfile` + `PyAV` dir at
`/cache/pyextra` with `PYTHONPATH` set (the image ships torchaudio / torchcodec /
ffmpeg / ffprobe but **not** soundfile/av), and raising `--limit-mm-per-prompt`
to `{image:16, video:1, audio:4}`. The engine log confirms `MMEncoderAttention
FLASH_ATTN` and an encoder cache budgeted at 114,688 tokens; the DFlash drafter
logs that it has no external-mm embeddings and drafts text-only for mm prompts
(the target still handles the multimodal tokens).

`scripts/bench-mm-mimo.py` — image drawn locally (PIL), speech WAV via
`espeak-ng`, red-square-sliding-right MP4 via ffmpeg. Live lane, 2026-10-03:

| input | result |
|---|---|
| image (red square / blue circle / green triangle / text "MIMO 42") | **correct** — all three shapes + colors and the text |
| audio `input_audio` (16 kHz WAV: "The secret password is purple elephant.") | **correct transcription** |
| audio `audio_url` | **correct** — password "purple elephant" |
| video (red square sliding right on white) | object **square** / color **red** correct; direction read as "diagonally top-left → bottom-right" (has the rightward component, not purely horizontal) |

Image throughput (`scripts/bench-mm.sh`, 1 image/request, 512×384 JPEG): C=1
**22.5 tok/s** (prompt 214 tok incl. the image), C=4 **62.9 tok/s** aggregate, no
errors. The mm encoder warms on the first request (first image call ~30 s, later
calls ~2 s).

Caveats: video direction is imperfect on this minimal clip (object/color are
right); audio depends on the prebuilt `pyextra` dir existing on both nodes; the
omni towers load regardless of modality, so text-only latency is unchanged.

## 9. GMU 0.90 evaluation (2026-10-04)

Question: is `--gpu-memory-utilization 0.90` safe on GB10? qwen38flash had to
drop 0.835 → 0.80 because a mixed-traffic soak left 0.3–0.9 GiB and the box
hard-reset. Measured on the live lane, sampling `MemAvailable` every 10 s on
both nodes:

| phase | node0 min | node1 min |
|---|---|---|
| idle baseline | 6.40 GiB | 7.58 GiB |
| C=8 sustained soak (~8 min, 3 rounds of 1,500-tok essays, `ignore_eos`) | **6.23 GiB** | 7.39 GiB |
| C=4 × ~32K-token concurrent prefill (20.7 s) | within the same window | — |

SwapFree stayed flat (no swap growth), `health` stayed 200, `cluster-node0` did
not restart. The KV pool is preallocated (16.24 GiB / 2,432,823 tokens / 9.28x
at 256K), so runtime pressure is activation + mm encoder cache, not KV growth.

**Verdict: GMU 0.90 is safe here** — headroom stays ≥ ~6.2 GiB, far above the
0.3–0.9 GiB danger zone. No change to 0.85 needed. (node0 runs ~1.2 GiB tighter
than node1, as expected: it also hosts the API/tokenizer.)
